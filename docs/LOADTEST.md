# Навантажувальне тестування

Тест виконано інструментом [k6](https://grafana.com/docs/k6/latest/). Сценарій: `loadtest/loadtest.js`, запуск: `loadtest/run.sh`.

## 1. Сценарій

Профіль «мало записів, багато читань»: один віртуальний користувач (VU) у циклі виконує одну операцію запису й одразу після неї 8 операцій читання. Між запитами є пауза 0,1–0,3 с, яка імітує поведінку людини.

| № | Запит | Призначення |
|---|---|---|
| 1 | `POST /api/cars/` | запис: створення автомобіля (потрібен JWT) |
| 2 | `GET /api/cars/?limit=20` | список |
| 3 | `GET /api/cars/{id}` | щойно створений запис |
| 4 | `GET /api/cars/?limit=20&sort=high` | список із сортуванням за ціною |
| 5 | `GET /api/cars/?limit=20&type=...` | список із фільтром за типом |
| 6 | `GET /api/cars/{id}` | один із записів, створених цим користувачем раніше |
| 7 | `GET /api/cars/total_price/` | агрегована інформація (сума цін) |
| 8 | `GET /api/cars/?limit=20&search=...` | пошук за брендом |
| 9 | `GET /api/cars/{id}` | щойно створений запис |

У застосунку немає сутності «автор», тому як окрему читальну операцію з агрегованими даними використано `total_price`. Співвідношення записів до читань дорівнює 1 : 8.

Усі запити списку мають параметр `limit=20`. Без нього кожен список повертав би всі записи, а їх кількість під час тесту росте на тисячі, тож відповіді стали б дуже великими й спотворили б вимірювання.

## 2. Фази навантаження

| Фаза | Тривалість | Кількість VU |
|---|---|---|
| Наростання | 3 хв | від 0 до N |
| Стале навантаження | 5 хв | N |
| Спад | 2 хв | від N до 0 |

Загальна тривалість тесту близько 10 хвилин. Поступове наростання потрібне, щоб не вимірювати розігрів (з'єднання з базою, перші запити) разом зі сталою роботою й щоб масштабування реагувало на зростання навантаження, а не на миттєвий стрибок.

## 3. Параметри

| Параметр | Значення |
|---|---|
| N (VUS) | _заповнити після підбору_ |
| Пауза між запитами | 0,1–0,3 с |
| Автентифікація | один вхід у `setup()`, токен оновлюється кожні 10 хв |
| Пороги (лише сигналізація) | частка помилок менше 5 %, p95 менше 1000 мс |
| Мінімум і максимум реплік | 1 і 4 (цільове завантаження CPU 60 %) |

### Як підібрано N

Один воркер gunicorn обробляє запити по черзі, тому одна репліка здатна обслужити обмежену кількість запитів за секунду. При N користувачах і паузі 0,1–0,3 с сумарний потік перевищує цю межу, процесор репліки доходить до цілі 60 % і більше, і платформа додає репліки.

- Початкове значення N = 40.
- Якщо кількість реплік не зростала, N збільшено.
- Якщо кількість реплік одразу досягала максимуму або з'являлись помилки, N зменшено.

_Заповнити: фінальне N і короткий опис, скільки спроб знадобилось._

## 4. Запуск

```bash
./loadtest/run.sh
```

Адреса сервісу й пароль адміністратора беруться з `terraform output`. Для іншого N:

```bash
VUS=60 ./loadtest/run.sh
```

Швидка перевірка сценарію:

```bash
VUS=2 RAMP_UP=10s STEADY=20s RAMP_DOWN=10s ./loadtest/run.sh
```

Файли з результатами зберігаються в `loadtest/results/`.

## 6. Висновки

_Заповнити: чи спрацювало масштабування, скільки реплік було на піку, як змінилась латентність у момент додавання реплік, чи були помилки й чому._

## 7. Пояснення метрик

- `http_reqs` це кількість усіх HTTP-запитів за тест.
- `http_req_failed` це частка запитів із помилкою: мережева помилка або статус 400 і вище.
- `http_req_duration` це час від відправлення запиту до отримання повної відповіді. У виводі k6 `med` дорівнює p50.
- p95 означає, що 95 % запитів виконались швидше за це значення, а p99 те саме для 99 %. Ці перцентилі показують повільні запити, які середнє значення приховує.
- Кількість запитів за секунду та кількість одночасних користувачів пов'язані через латентність: запитів за секунду приблизно дорівнює кількості користувачів, поділеній на суму часу відповіді та паузи.
