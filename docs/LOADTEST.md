# Навантажувальне тестування

Тест написано в k6. Файли: `loadtest/loadtest.js` (сценарій) і `loadtest/run.sh` (запуск).

## 1. Що робить тест

Кожен віртуальний користувач повторює цикл: **1 запис і 9 читань**. Між запитами пауза 0,2 с.

| № | Запит | Що це |
|---|---|---|
| 1 | `POST /api/cars/` | запис: створення автомобіля (потрібен токен JWT) |
| 2 | `GET /api/cars/?limit=20` | список |
| 3 | `GET /api/cars/{id}` | щойно створений автомобіль |
| 4 | `GET /api/cars/?limit=20&sort=high` | список із сортуванням |
| 5 | `GET /api/cars/?limit=20&type=sedan` | список із фільтром |
| 6 | `GET /api/cars/{випадковий id}` | випадковий автомобіль |
| 7 | `GET /api/cars/total_price/` | сума цін усіх автомобілів |
| 8 | `GET /api/cars/?limit=20&search=bmw` | пошук |
| 9 | `GET /api/cars/?limit=20` | список ще раз |
| 10 | `GET /api/cars/{id}` | щойно створений ще раз |

У застосунку немає «автора», тому замість нього використано `total_price` (сума цін). Параметр `limit=20` обмежує розмір відповіді: без нього список повертав би всі записи, а їх під час тесту стає тисячі.

## 2. Три фази

| Фаза | Тривалість | Користувачів |
|---|---|---|
| Наростання | 3 хв | від 0 до N |
| Стале навантаження | 5 хв | N |
| Спад | 2 хв | від N до 0 |

Усього 10 хвилин. Навантаження наростає поступово, щоб не вимірювати розігрів разом зі сталою роботою.

## 3. Запуск

З кореня репозиторію:

```bash
./loadtest/run.sh
```

Адреса сервісу й пароль адміністратора беруться з `terraform output`. Інше N:

```bash
VUS=80 ./loadtest/run.sh
```

Короткий пробний запуск (40 секунд):

```bash
QUICK=1 VUS=2 ./loadtest/run.sh
```

Вивід кожного запуску зберігається у `loadtest/results/`.

## 4. Параметри

| Параметр | Значення |
|---|---|
| N | _заповнити_ |
| Пауза між запитами | 0,2 с |
| Токен | отримується один раз на початку, діє близько 15 хвилин |
| Мінімум і максимум реплік | 1 і 4, ціль CPU 60 % |

**Як підібрано N.** Один воркер gunicorn обробляє запити по черзі, тому одна репліка витримує обмежену кількість запитів за секунду. Починали з N = 40 і збільшували, доки на сталому навантаженні кількість реплік не доходила до максимуму (4).

_Заповнити: яке N було спробувано і яке залишено._

## 7. Що означають показники

- `http_reqs` це кількість усіх запитів за тест.
- `http_req_failed` це частка запитів із помилкою (мережева помилка або статус 400 і вище).
- p50 означає, що половина запитів була швидшою за це значення. p95 і p99 означають те саме для 95 % і 99 % запитів. Вони показують повільні запити, які середнє приховує.
- Кількість запитів за секунду пов'язана з кількістю користувачів через латентність: запитів за секунду приблизно дорівнює кількості користувачів, поділеній на суму часу відповіді та паузи.
